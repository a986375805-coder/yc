GamePulse AI · 游戏节点聚合工具

展开 / 收起

交付内容
日历、四栏看板、测试排期与只读分享页
实际使用
个人独立运行；本人每日使用，同事查看结果

游戏测试、首发和版本信息分散在不同平台，人工整理既要找来源，也要判断日期与事件类型。我将采集、语义提取和复检串成流程，集中查看近期节点。

技术选择：采集与语义判断分开

对比 RPA 后，选择用采集程序取得页面内容，再由 LLM 区分公测、内测和新版本等事件，减少对固定页面操作路径的依赖。

关键实现：提取后再验证

  • 提取规则：先区分已上线与预约／测试中的游戏，再提取对应节点；返回游戏名、活动名、日期、测试类型、激活码与删档状态，减少把历史上线日期当成新事件。
  • 复检机制：结合搜索材料或联网模型，给出“确认／矛盾／无法验证”及依据和置信度。复用已有审核结果、合并相同节点；异常保留为“无法验证”，交由人工核对。
  • 数据可靠性：校验 JSON、处理缺失字段，调用失败时重试与退避；统一名称和日期，合并重复记录，对比已有数据标记新增或待审。

使用者看到什么

SQLite 保存游戏、节点与审核记录，日历和排期表提供不同查阅入口；节点保留来源，发现日期或类型疑问时可以回查原文。

使用方式

Word 稿件进入 CMS，需要在分类、标题、正文、图片和游戏标签之间反复切换。我将这些步骤组织成浏览器辅助流程，减少跨控件操作和遗漏。

核心亮点 / 异步 AI 能力接入

把稿件识别放进完整发布流程

正文写入后，扩展触发 CMS 既有的 AI 智能填充，等待游戏识别结果弹窗并执行确认。我的工作是组织调用顺序、等待条件、结果确认与异常提示；游戏与标签识别由 CMS 提供。

  1. 读取 DOCX
  2. 填充分类、标题与正文
  3. AI 识别游戏与标签
  4. 上传图片并回填
  5. 人工核对发布

01 / 文档解析与标题回退

用 Mammoth.js 转换 DOCX、抽取内嵌图片并建立编号占位符。标题支持文件名或文档 XML；按加粗段落、最大字号、首个非空段落逐级回退。

02 / 适配异步控件

等待分类树加载，定位分类、填写字段并写入富文本编辑器，触发输入与变更事件；正文首段与标题相同时自动去重。

03 / 图片上传与位置还原

图片转为 Blob，按条件压缩静态大图、跳过 GIF 压缩；读取上传状态与图片地址，再替换编号占位符，还原图文位置并保留尺寸信息。

04 / 失败后可以接着处理

用运行标记防止重复启动，逐步日志定位错误。AI 入口缺失、等待超时或图片失败时给出提示；保留重传图片和读取侧栏图片插入的人工补救入口。

实践场景
产品与前端角色围绕摘要展示规则协作

Agent 执行协作任务，需要把“读消息、查记录、更新任务”转成可调用的接口。我将飞书开放 API 组织为 CLI 与 Skill，统一身份处理、参数入口和返回结果。

关键实现：让接口能被连续调用

  • 请求与权限：使用 Python 标准库发起请求，从环境变量或独立配置读取凭据、获取访问令牌；集中处理 JSON、网络错误和飞书返回码。
  • 统一命令：按子命令分发消息、资源、表格、日历、任务和文档操作，配套 Skill 文档说明参数与权限要求。
  • 结构化输出：消息整理出类型、时间、发送者与正文；表格用字段 JSON 与筛选条件操作，便于后续任务继续处理。

协作案例：从产品要求到前端建议

为产品、数据、前端与日常助理编写角色模板，明确职责、项目上下文和协作约定。实际讨论中，产品角色澄清摘要展示与换行规则，前端角色给出样式和实现建议，再根据反馈细化。

产品改版 · 需求设计 / 交互原型

游戏榜单 · 从排名列表到游戏发现入口

展开 / 收起
我的职责

交付内容
总需求、前后端规则、交互原型与评审讲稿

排名能表达热度，却不能直接说明“近期有什么变化”。我围绕游戏发现路径，把主榜、分类、本周节点和站内详情入口组织在一起。

信息架构：主榜与近期关注分工

热门／期待榜分别承载已可体验与待上线游戏，侧栏补充“本周值得看”。宽屏双栏、窄屏上下排列，详情入口统一进入站内游戏资料页。

内容规则：摘要必须对应同一节点

卡片展示日期、类型、名称与一句话摘要，说明该次测试或更新；节点与摘要分别做空值处理。本周模块选择最近的有效推荐节点，最多展示 12 款，不凑数。

分类交互：筛选不重排名

分类单选、重复点击取消；筛选后保留原榜顺序并隐藏名次，避免子集被误解为独立排名。切换榜单时清空分类并回到顶部。

失败处理：区分缺少候选与采集故障

正常候选不足按规则继续补位；采集失败或不完整时使用有效的完整历史榜单。没有可用备份才展示暂不可用，避免故障被显示为空榜。

排序与数据关系，写到研发可以判断

  • 多来源合并：不直接比较跨平台原始分数，保留来源顺序、安排展示位置，在实际填充时去重并继续取下一项。
  • 候选边界：区分正式游戏、DLC、试玩与合集，分别处理已可体验、抢先体验和仅预购状态。
  • 字段关系：分别定义游戏资料、时间节点和榜单记录；推荐标记与编辑徽标独立，避免状态混用。

游戏历程后台配置需求说明

配合游戏历程前台插卡，我设计后台配置能力，让运营选择节点展示样式，并用联动约束和默认值避免无效配置、保护历史内容。

先约束样式，再配置内容

封测、内测、日常更新锁定“不设置”；公测、新版本、资料片开放默认／图文样式。说明与宣传图按样式区分必填条件。

前台只读取有效配置

按节点类型与样式开关过滤，按时间倒序展示最新 4 个节点，其余放入历史浮窗；说明为空时隐藏灰底卡片，保留时间轴。

保留内容编辑的明确边界

内容标签支持 1–6 组，包含分类标签、小标题与详细文本；达到上限禁用添加，只剩一组禁用删除。

历史数据采用安全默认值

历史公测／新版本节点默认“不设置”并继承原说明，避免旧文案直接进入新样式；先调整重点游戏，再逐步开放展示。
